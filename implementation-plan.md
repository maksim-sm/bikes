# План реализации фронтенда интернет-магазина велосипедов

План для ИИ-разработчика. Основан на [`project-design-document.md`](./project-design-document.md) (далее — ДД) и правилах [`AGENTS.md`](./AGENTS.md). Кода в плане нет — только инструкции, что сделать и как проверить.

---

## 0. Как работать с планом

### 0.1. Порядок

- Шаги выполняются **строго по порядку**. Шаг можно начинать, только если все предыдущие завершены и проходят проверки.
- Один шаг — одна ветка/один коммит (или серия коммитов) с сообщением «Шаг N: <название>».
- Не реализуй в шаге то, что запланировано в следующих шагах. Если без этого не обойтись — остановись и сообщи.
- Если шаг противоречит ДД — следуй ДД и отметь расхождение в итоговом сообщении.

### 0.2. Структура шага

Каждый шаг содержит:

- **Сделать** — конкретные действия.
- **Тесты** — какие тесты написать в рамках шага. Метки: `[unit]` — Vitest, `[RTL]` — Vitest + React Testing Library, `[e2e]` — Playwright, `[axe]` — проверка доступности axe-core в Playwright, `[LH]` — Lighthouse CI.
- **Готово, когда** — критерии приёмки.

### 0.3. Базовая проверка (выполняется после КАЖДОГО шага)

Далее — «Базовая проверка». Шаг не считается завершённым, пока она не пройдена:

1. Проверка типов TypeScript — без ошибок.
2. Линтер — без ошибок и предупреждений.
3. Все unit- и компонентные тесты (Vitest) — зелёные, включая написанные в прошлых шагах.
4. Smoke-набор Playwright — зелёный: все уже существующие страницы открываются без ошибок в консоли и без ответов 5xx.
5. Smoke-набор axe — на всех существующих страницах нет нарушений уровней `serious` и `critical`.
6. Production-сборка проходит без ошибок.
7. Изменённые страницы просмотрены в браузере на ширине 375 px и 1280 px.

С шага 6 базовая проверка дополнительно включает Lighthouse CI (на страницах, перечисленных в его конфигурации).

### 0.4. Соглашения по тестам

- Unit- и компонентные тесты лежат рядом с тестируемым файлом с суффиксом `.test.ts(x)`.
- E2E-тесты — в каталоге `e2e/`, по одному файлу на сценарий или страницу. Каждый новый e2e-файл добавляется в smoke-набор, если он проверяет открытие страницы.
- В тестах моки работают **без искусственной задержки** и детерминированно. Режим ошибок мок-API включается флагом окружения или заголовком запроса — так тестируются состояния ошибки.
- Селекторы в RTL и Playwright — по ролям и доступным именам (кнопка «В корзину», заголовок уровня 1), а не по CSS-классам. Если элемент не находится по роли — это сигнал проблемы доступности.
- Тексты в тестах берутся из словаря `lib/i18n/ru.ts`, а не дублируются строками.
- Тест сначала должен упасть без реализации (проверь это хотя бы для ключевой логики: цены, размеры, подбор, итоги заказа).

### 0.5. Целевые пороги

| Проверка | Порог |
| --- | --- |
| Lighthouse Performance (мобильный профиль) | ≥ 90 |
| Lighthouse Accessibility | ≥ 95 |
| Lighthouse Best Practices / SEO | ≥ 95 |
| LCP / INP / CLS | < 2.5 с / < 200 мс / < 0.1 |
| JS первой загрузки | < 200 КБ gzip |
| axe | 0 нарушений `serious` / `critical` |
| Покрытие `lib/` (format, sizing, podbor, validation, api) | ≥ 90% строк |
